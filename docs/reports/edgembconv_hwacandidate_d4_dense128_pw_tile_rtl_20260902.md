# EdgeMBConv hardware-aware candidate D4 — dense128 PW tile RTL evidence

This is an independent D4 candidate artifact.  It does not modify C0, any C0
training/checkpoint path, or the production `cnn_layer_runner` path.  The RTL
owns one 8-pixel × 16-Cout output-stationary tile with 128 signed INT8 MAC
cells; it does not instantiate two legacy 8×8 engines.  The cell has explicit
operand registers, a registered DSP product/M stage, and a registered INT32
accumulator.  Transaction tags (valid, first/last, K, masks, and metadata)
traverse the same two pipeline boundaries.

## Real-vector functional evidence

The vectors were generated by
`python/export_edgembconv_hwacandidate_d4_dense128_vectors.py` from the D4
deployment archive
`build/edgembconv_hwacandidate_d4/edgembconv_hwacandidate_d4_deploy/edgembconv_hwacandidate_d4_int8.npz`
(SHA256 `5804204e0ba2bd23e8e40dcfc656007838935d28692279401ae058822775dbe7`)
and official CIFAR-10 test sample 0 (label 3).  The activation source is the
exported integer stem followed by the real D4 `mb32` residual and
`mb16_down` stages; weights are the exported D4 INT8 weights.

| Real D4 tile | Cin/K tokens | raw products | arithmetic ops (2 per MAC) |
| --- | ---: | ---: | ---: |
| `mb32.expand` | 16 | 2,048 | 4,096 |
| `mb16.1.expand` | 32 | 4,096 | 8,192 |

Each tile has 128 expected signed INT32 psum lanes.  Vector file hashes and
metadata are recorded in
`build/edgembconv_hwacandidate_d4_dense128_vectors/d4_dense128_vector_manifest.json`.

The testbench checks exact psums and all 128 lane masks for both tiles,
first/last/K metadata, 3-cycle stability of every output field while stalled,
blocked input stability, exact accepted-token count, exact 128-lane coverage
per tile, and no token loss/duplication.  K=32 is therefore exercised with a
real D4 deployment layer, not only with random data.  The source inserts
repeatable bubbles; the pipeline check observes II=1 between bubbles and a
fixed two-cycle startup/drain delta relative to the pre-pipeline primitive.

The cycle-model comparison is intentionally boundary-aware:

| Contract | Ideal | Boundary startup/fence | 3-cycle output stall |
| --- | ---: | ---: | ---: |
| `mb32.expand`, K=16, schedule's vector4 writeback model | 48 | 50 | 53 |
| 128-MAC raw-psum tile, K=16 (observed with source bubbles) | 39 pre-pipeline | +2 fixed pipeline cycles | 41 raw primitive cycles |
| 128-MAC raw-psum tile, K=32 (observed with source bubbles) | 77 pre-pipeline | +2 fixed pipeline cycles | 79 raw primitive cycles |

The 48/50/53 schedule includes 32 vector4 writeback commits and is not
claimed as the latency of this raw-psum-only primitive.  Once integrated, its
fixed pipeline contribution is bounded to two cycles per tile; full D4 block
and full-network cycle evidence remain integration gates.

## XC7Z020 OOC post-route screen

Run script:
`scripts/run_edgembconv_hwacandidate_d4_dense128_pw_tile_ooc_threads8_20260902.ps1`

Output directory:
`build/reports/vivado_edgembconv_hwacandidate_d4_dense128_pw_tile_ooc_threads8_20260902`

Device `xc7z020clg400-1`, clock period 8.000 ns, Vivado 2025.2,
`general.maxThreads=8`.  The Vivado log records 8-CPU multithreading for
place, phys-opt, and route; route status reports zero routing errors and zero
unrouted nets.

| WHS / THS | +0.148 ns / 0.000 ns | pass |
| Slice LUT | 8,566 (16.10%) | <70% |

The fresh post-route worst setup path is the high-fanout `token_first` tag to
an `operand_clear` register: 7.133 ns data-path delay and +0.580 ns slack.
The registered product path is separate from the activation-to-accumulator
cone (the reported product path has +0.994 ns slack).  Route status has zero
routing errors and 0 unrouted nets.  This remains only an OOC primitive
screen, not a claim of full-network closure, cycle count, or energy
efficiency.
