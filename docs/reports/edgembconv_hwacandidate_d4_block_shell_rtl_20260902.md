# EdgeMBConv hardware-aware candidate D4 — block shell gate

This is an independent candidate artifact.  It does not modify C0, its
training/checkpoint paths, the legacy runner, or the production top level.

## Frozen blocks and arithmetic

The shell accepts the exact folded INT8 deployment parameters from
`edgembconv_hwacandidate_d4_int8.npz` and runs two complete D4 blocks:

| block id | frozen name | input -> output | stride | residual | output bytes |
|---:|---|---|---:|---|---:|
| 0 | `mb32` | 32x32x16 -> 32x32x16 | 1 | yes | 16,384 |
| 1 | `mb16_down` | 32x32x16 -> 16x16x32 | 2 | no | 8,192 |

The PW schedule uses one 8-pixel x 16-Cout tile with 128 signed INT8
multiply/accumulate lanes, reused for expand and project.  The DW schedule
uses one 16-lane (16-DSP) 3x3 engine, one tap per cycle.  SAME halo coordinates
are explicitly zeroed, stride-2 sampling is explicit, and all channel tails
are masked by the block dimensions.  Two local scratch images carry explicit
`FREE -> FILL -> READY -> ACTIVE -> FREE` ownership and epoch fences.  The
complete expansion is never sent to global SRAM.

## Exact simulation

Vectors were generated by
`python/export_edgembconv_hwacandidate_d4_block_shell_vectors.py` from the
frozen D4 deployment archive and official CIFAR-10 test sample 0.  The Python
reference uses the same folded bias, nearest-away-from-zero requantization,
INT8 saturation, and common-scale residual add as deployment evaluation.

Command:

```text
python python/export_edgembconv_hwacandidate_d4_block_shell_vectors.py
wsl.exe bash -lc 'cd /mnt/d/Stuff/Project && bash scripts/run_edgembconv_hwacandidate_d4_block_shell_sim.sh'
```

Result:

```text
D4_BLOCK block=0 name=mb32 output_bytes=16384 cycles=63465 pw_mac=1048576 dw_mac=294912 overlap=0 scratch=00/00 errors=0
D4_BLOCK block=1 name=mb16_down output_bytes=8192 cycles=20597 pw_mac=1835008 dw_mac=368640 overlap=0 scratch=00/00 errors=0
PASS edgembconv_hwacandidate_d4_block_shell blocks=2 exact_bytes=24576 protocol_errors=0
```

The shell counters are cumulative across the two back-to-back transactions;
therefore the second line's `pw_mac`/`dw_mac` values include `mb32`.  The
block-local counts are 786,432 PW MACs and 73,728 DW MACs for `mb16_down`, as
shown in the table below.

The testbench compares every output byte and output index, applies regular
ready/valid output stalls, checks output index stability while stalled, and
checks that both scratch banks observed FILL, READY, and ACTIVE before being
released.  The observed arithmetic totals are exact:

| block | PW MACs | DW MACs | semantic MACs | measured shell cycles | gate |
|---|---:|---:|---:|---:|---|
| `mb32` | 1,048,576 | 294,912 | 1,343,488 | 63,465 | <=90,000 PASS |
| `mb16_down` | 786,432 | 73,728 | 860,160 | 20,597 | <=28,000 PASS |

The shell's measured schedule is serialized at this gate; `overlap=0` is
intentional and honest.  A future dual-issue scheduler must provide actual
DW/current-tile and PW/next-tile concurrency before overlap is credited.

## XC7Z020 OOC attempt (2026-09-02)

The independent entrypoint
`scripts/run_edgembconv_hwacandidate_d4_block_shell_ooc_threads8_20260902.ps1`
was run against Vivado 2025.2 and `xc7z020clg400-1`.  The Tcl root expression
and OOC synthesis flow were corrected before this run, and the actual log
reports `general.maxThreads=8` with synthesis multithreading enabled (Vivado
reported a maximum of 7 helper processes).

The run entered `synth_design` successfully, but after approximately 40
minutes it had produced no synthesis, placement, route, utilization, timing,
power, or checkpoint artifact.  It was interrupted while still in synthesis;
the preserved log is
`build/vivado_edgembconv_hwacandidate_d4_block_shell_ooc_threads8_20260902.log`.
This is a synthesis-scale blocker/negative gate for the current full shell,
not a timing or resource result.  No C0 or production path was changed.
